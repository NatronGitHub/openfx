# Release Notes - NEXT (upcoming)

This is version NEXT of the OpenFX API.

## Key Features of OpenFX Version NEXT:

- **Unlicensed-render behaviour**: Added `kOfxImageEffectPropBehaviourWhenUnlicensed` so a host can tell plugins whether to fail a render or render anyway (e.g. watermarked) when unlicensed (issue #202).
- **Parameter interpolation types**: Added `kOfxParamInterpType` and related definitions documenting standard keyframe interpolation modes (issue #116).
- **Obsolete plugins**: Added `kOfxImageEffectPluginPropObsolete` so a plugin bundle can mark a plugin as obsolete: available for use in old projects but not offered to users for new use (issue #221).
- **Windows ARM64 packaging**: Defined plugin install locations for Windows on ARM, including the new normative `Win-arm64ec` folder for Arm64EC/Arm64X plug-ins, with most-specific-first DLL search order (issue #160).
- **Clip display time offset**: Added `kOfxImageClipPropDisplayTimeOffset`, the frame number the host displays for time 0 (e.g. 1001), so a plugin's own UI can show the same frame numbers as the host. Its string value keeps a leading `k` for compatibility with hosts and plugins that already use it (issue #58).
- **Colour-Managed Colour Params**: Added `kOfxParamPropColourManagement`. Lets a plugin declare the colourspace of an RGB/RGBA parameter's values (including its default): `Managed` (ACES2065-1, scene-linear, unclamped) for processing colours, or `SRGB` (sRGB, [0..1]) for display-referred UI colours such as Draw Suite overlays, so a host can interpret and convert them correctly (issue #158).
- **Metal texture rendering**: Added `kOfxImageEffectPropMetalTextureSupported` and `kOfxImageEffectPropMetalTextureEnabled` so a host can pass images to Metal plug-ins as `id<MTLTexture>` instead of `id<MTLBuffer>`, negotiated alongside the existing Metal buffer path. Proposed by Greg Cotten (Video Village); already implemented by Pomfort Livegrade (host) and Video Village Scatter (plug-in) (issue #283).
- **Keyboard modifiers in interacts (Natron extension)**: Added `kNatronOfxInteractPropKeyModifiers` (a bitmask of `kNatronOfxKeyModifierShift`, `Control`, `Alt` and `Meta`) to `ofxNatron.h`, extension 13, set by the host in the inArgs of the interact actions of image effect overlays and parameter interacts, and the host property `kNatronOfxInteractHostPropSupportsKeyModifiers`. Extension 13 mirrors the proposed OFX 1.6 `kOfxInteractPropKeyModifiers`, `kOfxInteractHostPropSupportsKeyModifiers` and `kOfxKeyModifier*`, with the same semantics and values; the modifiers are only passed to interact actions, not to `instanceChanged`. The Support library adds `OFX::ImageEffect::getKeyModifiers()` (and `isShiftDown()`, `isControlDown()`, `isAltDown()`, `isMetaDown()`, `InteractArgs::keyModifiers`), which uses the property when the host passes it and tracks the modifier key events of the instance's overlays otherwise, and also reads the `kOfx` names when `ofxInteract.h` defines them; HostSupport declares the property for the interacts whose `Interact::Instance::supportsKeyModifiers()` returns true when the host application sets `kNatronOfxInteractHostPropSupportsKeyModifiers`, and sets it from `getKeyModifiers()` (NatronGitHub/openfx#134, NatronGitHub/openfx#140; issue NatronGitHub/openfx#131). The Support library also gets `OFX::Interact::getEffect()`, the effect instance of an interact (not only with the Natron extensions).
- **OpenGL DrawSuite core (`include/ofxDrawSuiteOpenGL.h`, fork addition)**: a header-only C++98 implementation of the OFX 1.5 DrawSuite with OpenGL 1.1 compatibility-profile calls, in namespace `OFX::DrawSuiteOpenGL`, shared by the Support library (the OpenGL backend of `DrawArgs::getDrawContext()`) and by hosts that implement the DrawSuite with OpenGL, so that a DrawSuite overlay looks the same in both. It includes no OpenGL header: the caller fills `GLFunctions` (13 OpenGL 1.1 functions) with `loadGLFunctions()` and its own symbol lookup. It has the DrawSuite state (`State`, `resetState()`), the DrawSuite functions (`standardColour()`, `setColour()`, `setLineWidth()`, `setLineStipple()`, `validatePrimitive()`, `drawPrimitive()`, `drawText()` with the built-in 5x7 font) and their building blocks (`ScopedGLState`, `applyLineState()`, `stipplePattern()`, `ellipseSegmentCount()`, `TextMetrics`, `builtinTextMetrics()`, `drawBuiltinText()`, `alignText()`), plus optional drop shadows (`State::shadows`, off by default; plug-ins never draw shadows with DrawSuite calls). The built-in font moved from `Support/Library/ofxsFont5x7.h` to `include/ofxFont5x7.h`. New self-test: `Support/tests/DrawSuiteOpenGLTest.cpp` (CMake target `drawsuite-opengl-test`, a fake OpenGL table, run on Linux, macOS and Windows).
- **HostSupport: OpenGL DrawSuite helper (`HostSupport/include/ofxhDrawSuiteOpenGL.h`, fork addition)**: `OFX::Host::Interact::OpenGLDrawSuite`, an optional header-only class that implements the DrawSuite hooks of `Interact::Instance` with the OpenGL DrawSuite core, as a member of the host's interact instance (composition): `beginDraw(pixelScale, screenPixelRatio, shadows)` at the start of each draw action, then `getColour()`, `setColour()`, `setLineWidth()`, `setLineStipple()`, `drawPrimitive()` and `drawText()` from the hooks. A host overrides `getColour()` (its own standard colours), `measureText()`/`renderText()` (its own font: `renderText()` gets the left end of the baseline and the metrics; without them, the built-in font) and `renderPrimitive()` (default: the core). With shadows on, the helper draws each line, strip, loop, ellipse outline and text twice, first offset by one device pixel right and down in the host's background colour (`getColour()`); filled rectangles and polygons get no shadow. The protected virtuals `shadowColour()` and `shadowOffset()` let a host use another colour (e.g. black instead of a grey viewer background) or another offset. If `renderText()` returns `kOfxStatReplyDefault` (a view that can't render text, e.g. Natron's CustomParamInteract), the helper draws that text with the built-in font. Natron will use it in NatronGitHub/Natron#1349: the OpenGL table from its glad loader, the overlay colours of its settings, Qt text through `measureText()`/`renderText()`, and its global overlay-shadow setting through `drawSuiteShadows()`.
- **DrawSuite shadows (Natron extension 14)**: `kNatronOfxInteractPropDrawSuiteShadows` (`ofxNatron.h`), an int in the inArgs of `kOfxInteractActionDraw`, read-only, 0 if absent: 1 if the host wants drop shadows on DrawSuite elements: the lines, line strips and loops, ellipse outlines and text get a shadow offset by one device pixel right and down, as the OpenGL shadows of the Natron and SupportExt overlays (pixel scale / screen pixel ratio in canonical coordinates); filled rectangles and polygons don't, so that translucent fills stay clear. The shadow colour is the host's background colour in the host's DrawSuite, and black in Support's emulation, which can't query the host. They are drawn by the host's DrawSuite implementation and by the Support library's DrawSuite-to-OpenGL emulation (V1 draws, `DrawArgs::getDrawContext()`, feature macro `OFXS_SUPPORT_HAS_DRAWSUITE_SHADOWS`, with `OFX_EXTENSIONS_NATRON`); plug-ins never draw shadows with DrawSuite calls, and OpenGL drawing code keeps its own. A plug-in that draws through `getDrawContext()` must not add its own shadow loop when the host sets the property (the shadows would be doubled). HostSupport sets it (with `OFX_EXTENSIONS_NATRON`) from the new `Interact::Instance::drawSuiteShadows()`, false by default. Plug-ins need a clean rebuild (the layout of `OFX::DrawContext`, and so of `OFX::DrawArgs`, changed), and so do HostSupport hosts (the `Interact::Instance` vtable changed).
- **HostSupport Python bindings, part 1 (fork addition)**: `-DOFX_PYTHON_BINDINGS=ON` builds `ofxh`, a nanobind module of HostSupport (Python >= 3.10, nanobind, NumPy), to write OFX hosts in Python, in-process (NatronGitHub/openfx#136). Python subclasses `ofxh.Host`, `ofxh.ImageEffectInstance` and `ofxh.ClipInstance` and overrides their callbacks (the defaults are hostDemo's); HostSupport owns C++ adapters that call them, and the Python objects of deleted adapters raise `ReferenceError`. Images are zero-copy NumPy arrays (`ofxh.ImageData`, bottom-up, any row stride). An exception in a callback never reaches HostSupport or the plug-in: the call fails, and the action re-raises it as `ofxh.CallbackError` (`ofxh.OfxError(status)` gives a status). Part 1 covers the actions of a render (`create_instance_action()`, `get_clip_preferences_action()`, the RoD, RoI, isIdentity, frames needed, begin/render/end sequence, time domain and instance changed actions, and `close()`), with C++ parameters that store their value (no keys), on the calling thread. `HostSupport/examples/python/minimal_host.py` is a one-page template host; its Invert renders are bit-identical to hostDemo's.
- **HostSupport Python bindings, part 2 (fork addition)**: parameters, descriptors, the GIL and packaging (NatronGitHub/openfx#136). `ImageEffectInstance.new_param(descriptor)` may return an `ofxh.Param` subclass, whose `get(time)` (always a time: the current one for paramGetValue), `set(value, time=None)`, `derive(time)`, `integrate(t1, t2)`, keyframe methods (`num_keys`, `key_time`, `key_index`, `delete_key`, `delete_all_keys`) and `changed(prop_name)` hook (the plug-in's setEnabled, setSecret...) hold the parameter in Python, for every parameter type but parametric; None keeps ofxh's C++ parameter, which now has keys and hostDemo's interpolation (linear, rounded for integers, held for booleans and choices), so the host descriptor now says that choices and booleans animate. `set_param(name, value, time=None)` sets a key at a time, `param_keys()`, `param_values()`, `param_initial()` (and `Param.initial`: the normalised spatial defaults in canonical coordinates) and `param_descriptor()` read them, and `press(name)` presses a push button (instanceChanged, reason user edited); values set before `create_instance_action()` (a project load) still send no instanceChanged. `Plugin.descriptor(context)` gives read-only copies of what the plug-in described (`ofxh.EffectDescriptor`, `ofxh.ParamDescriptor`, `ofxh.ClipDescriptor`), `ofxh.describe(plugin, context=None)` hostDemo's `--describe` JSON, and `ofxh.param_template(plugin, context)` the defaults of the parameters as JSON-serialisable data. The GIL is released while HostSupport and the plug-in run (the actions, the plug-in scan, `create_instance()`); every callback takes it again, and a call from another thread during an action raises RuntimeError. Each action with a time moves the default timeline to it first, as hostDemo; an action called from a callback of another one restores the outer time. A plug-in's worker thread inside a callback may call the bindings that run no action. `HostSupport/python/pyproject.toml` (scikit-build-core) builds the module alone: `pip install ./HostSupport/python`.
- **HostSupport Python bindings, part 3 (fork addition)**: the in-process backend of `ofxhost` (NatronGitHub/openfx#136). `ofxhost.render()` and `ofxhost.describe()` take `backend="subprocess"` (hostDemo, the default) or `"inprocess"` (also `$OFXHOST_BACKEND`): `ofxhost.inprocess` is hostDemo's test host ported to Python on `ofxh`, with the same API, the same inputs, actions, render windows and errors, and the same JSON report (`--report`), without files (each input fetch gives the plug-in a new NumPy array at the clip's depth, which ofxh passes without another copy; outputs are the arrays the plug-in rendered into). The ofxhost and Support/Plugins tests run on both backends (`ofxhost.testing`'s `backend` fixture; `@pytest.mark.backends(..., reason=...)` marks a test that depends on one), and new tests check that both give the same pixels and reports. `ofxh.init(..., profile="ofx14")` is an OFX 1.4 host, as hostDemo `--ofx14` (only the OFX 1.4 host properties and suites, no OfxSetHost; `ofxh.profile()`). `ofxh.init()` still allows one host per process (RuntimeError, now saying why), and the in-process backend refuses to replace a host it didn't start. Also: `del PropertySet[name]` for the host's properties, `ImageEffectInstance.param_props(name)` (the instance's parameter properties, e.g. enabled), and `ImageEffectInstance.default_output_depth` (the output depth of the default clip preferences when no input is connected; hostDemo's `-d`). CI runs the ofxh tests with all the extensions on (Linux), and the ofxhost tests on both backends (Linux, and the weekly macOS job).
- **HostSupport Python bindings, part 4 (fork addition)**: the sample host on `ofxh` and its command line (NatronGitHub/openfx#136). `ofxhost.graph` graphs now save to JSON and load back (`Graph`, `Graph.of(*outputs)`, `save()`, `dumps()`, `load()`, `loads()`; schema `ofxhost.graph` version 1): nodes with their plug-in versions, connections, values, keys (`Keys`, with their interpolation), file parameters (`FilePath`), push button presses, image sequence inputs (`Files`), the outputs and their file name patterns, the frames, render scale, window and depth, and the project; a graph saved and loaded is equivalent, and saving it again gives the same bytes. `save()` to another directory rewrites the relative paths for it. An input clip that a graph doesn't give is disconnected (the test patterns are asked for by name), and unknown keys are refused. `ofxhost.graph.load()` now returns a `Graph` (`.output`, `.nodes`) instead of the `(output, nodes)` tuple of part 1. `ofxhost.graphhost.run(graph, plugin_dirs)` runs a graph over a frame sequence in-process, with in-memory images between the nodes: the parameter values and keys are loaded before `kOfxActionCreateInstance` (a project load, without instanceChanged), push buttons are pressed after it, the frames are the outputs' time domains (`getTimeDomain` in the general, reader, writer and generator contexts, as Natron, or the spec's default: the union of the non-optional inputs' frame ranges), each node's begin/end sequence render gets the frames it renders, the frames and regions the plug-ins need are rendered before each render action (temporal effects work), identities aren't rendered, and image sequences and the plug-ins' file parameters use Natron's file name patterns (`####`, `%04d`, `%d`, `%v`, `%V`, `%%`; `ofxhost.sequences`), with a reader's `originalFrameRange` set from its files, and file parameters relative to the graph's directory; it writes a JSON report (`ofxhost.graphReport`), and a failure (a bad graph or file, a failed action) ends the run with the error in the report instead of raising. `python -m ofxhost` (`ofxhost.cli`, after pyofx's; exit status 1 for a failed run, 2 for a usage error) has `list`, `params` (`-j`: a one-node graph template from `ofxh.param_template()`), `filter` and `render` (`--dump`, `--save-graph`, `--report`). `ofxh`: `ImageEffectInstance.set_param()` takes a choice's option label as well as its index, and `param_curve(name)` gives a parameter's keys with their values. Also: the in-process backend takes hostDemo's `-s ASSIGNMENT` in `extra_args`, and without `PYTHONPATH` it imports the `ofxh` module of the build tree of the plug-ins (`$OFX_TEST_PLUGIN_PATH`), or asks for `PYTHONPATH` when several build trees have one.
- **HostSupport Python bindings, part 5a (fork addition)**: the Python host can replace hostDemo in the plug-in repositories' tests (NatronGitHub/openfx#136). `ofxhost.hostdemo` (`python -m ofxhost.hostdemo`, `python -m ofxhost hostdemo`, or the `HostSupport/examples/python/hostdemo-inprocess` script) is hostDemo's whole command line on the in-process backend, a drop-in for the hostDemo binary in their scripts: the same options and errors, the plug-ins of `$OFX_PLUGIN_PATH` (with `OFX_HOSTDEMO_KEEP_LOADED=1`), the same PPM/PFM output files, `--report` and `--describe` JSON, messages on stdout and exit status, one run per process; its tests run the repositories' command lines with both and compare the files byte for byte. What differs from hostDemo: the report's `host.name` and absolute `plugin.filePath`; JSON numbers written by Python (`0.0`, not `0`; NaN and infinities `null`, as hostDemo); means that can differ in their last bits; no nested RoD action for the output fetches of a render (plug-ins that trace actions print fewer); `--no-cache` a no-op and a shorter plug-in list without `--quiet`; ofxh's StrChoice values limited to their enums; a Python-host bug exits 1 with a traceback and no report. On Windows, `python -m ofxhost.hostdemo` with `;`-separated Windows paths in `PYTHONPATH` (the script converts them when `cygpath` exists); CI runs it on UCRT64 against hostDemo.exe. The in-process `ofxhost.render()` also takes `--format ppm|pfm`, `-o` and `--report` in `extra_args` (the files and report as hostDemo writes them). Per-input components, in-process and in the sample host only (hostDemo is frozen): `render(..., components={"Source": "rgb"})`, or a `#rgb`, `#alpha` or `#rgba` suffix on an input spec (`"ramp#rgb"`, `Files("in.####.pfm#rgb")`), gives the clip an RGB or Alpha input; the clip preferences then choose its components (`ofxhost.split_components()`). A plug-in's worker threads may now be the first to fetch the output image of a render, also several at once (one image per render: the bindings no longer make, and leak, one per concurrent first fetch), or ask for the output's RoD during it: both hosts return the RoD computed before the render action, without running the action on the worker. The report writes NaN and infinite statistics as `null`, as hostDemo does. `ofxh.init(..., keep_loaded=True)` (`Host::keepPluginsLoadedAfterScan()`) and `ofxh.keep_loaded()`. HostSupport's default `ClipInstance::findSupportedComp()` now maps RGB to RGBA (else Alpha) for a clip that doesn't support RGB, as Natron's override does (it gave `kOfxImageComponentNone`; hostDemo never gives RGB inputs). The sample host plans a node again only when the union of the windows asked of it at a time grows (deep diamond-shaped graphs). `$OFXHOST_PRELOAD` loads libraries before the plug-in scan (e.g. libtbbmalloc for IO.ofx). The README has a MIGRATION section: each hostDemo command line of the repositories and its Python-host equivalent.
- **HostSupport Python bindings: batch mode of `ofxhost.hostdemo` (fork addition)**: `python -m ofxhost.hostdemo --batch FILE|-` (or `ofxhost.hostdemo.run_batch(commands, jobs=1, timeout=None, host="fresh")`) runs many hostDemo command lines in one Python, in a pool of worker processes (`-j N`), instead of paying the start of Python and the imports of NumPy and `ofxh` for each (NatronGitHub/openfx#136). One command line per line (POSIX shell quoting, `#` comment lines, optional leading `--cwd DIR`, `--env NAME=VALUE` and `--timeout SECONDS`); each runs as a separate run would (its own output files, `--report` and `--describe` JSON, exit status, and stdout and stderr captured into files that survive a worker's crash), and gives a JSON record (`line`, `args`, `cwd`, `env`, `exitStatus`, `ok`, `stdout`, `stderr`, `seconds`, `crashed`, `timedOut`, `worker`, `seq`) on stdout or in `--batch-report FILE`, followed by records of worker events (a worker that died between two commands, or failed at its end). A command whose worker dies (a signal, `exit()`) or that runs past its timeout is recorded as crashed or timed out (after a dump of the worker's Python stacks), its worker is killed with its process group and replaced, and the batch goes on; the exit status is 1 if any command failed or a worker event occurred (2: a usage error, 3: an internal error); the workers run in their own process group, which the batch kills on SIGTERM and SIGHUP, and end if the batch dies. By default each command gets a new OFX host, as with hostDemo; `--fresh-host-per-plugin` keeps it while the plug-in is the same, and `--reuse-host` while the plug-in directories, profile and options are (the fastest, but the plug-ins' globals and the plug-in scan are shared by a worker's commands); a kept host is shut down before the next command starts, so its unload output or crash isn't blamed on that command. On macOS arm64 (README.md, MIGRATION; median of 3), openfx-misc's `rendertest.sh` command lines (236) take 6.7 s with `--batch -j 4` (the default, a new host per command), 6.1 s with `--reuse-host`, against 14.9 s for one `python -m ofxhost.hostdemo` process per command 4 at a time and 13.0 s for hostDemo 4 at a time. In every mode, the output files and reports were the same as the separate runs' byte for byte, and the exit statuses and stdout the same; stderr was the same too, except that with a kept host what plug-ins print during the plug-in scan is only in the stderr of the host's first command. The in-process report now lists the clips of `framesNeeded` and `regionsOfInterest` by name (HostSupport's maps are ordered by the clips' addresses, which varied between runs).

- **CMake: combined or separate plug-in bundles**: `ofx_plugin_bundle_group()` in `cmake/OpenFX.cmake` builds a group of OFX plug-ins as one combined bundle (the default) or as one bundle per plug-in (`-DOFX_PLUGIN_BUNDLES=SEPARATE`, or `OFX_PLUGIN_BUNDLES_<group>` for one group), the CMake equivalent of the Makefiles' `make nomulti`, with other names: separate bundles are named after the plug-in identifier (e.g. `net.sf.openfx.Merge.ofx.bundle`, where `make nomulti` makes `Merge.ofx.bundle`), so that packages can't collide in a shared plug-in folder (packagers who installed the old Makefile bundles may get duplicates); their target and install component are the short plug-in name. It handles per-bundle Info.plist and resources (files, directories, `DESTINATION` subdirectories, with clash detection), common objects, per-plug-in compile settings, OpenMP, plug-ins that also ship separately (`ALSO_SEPARATE`), combined-only and separate-only plug-ins, target properties for the caller, and manual registration (`REGISTER`) on top of the Support library's automatic registration. See `Documentation/proposals/cmake-plugins.md`.

## Behaviour Changes

Changes that existing hosts, plugins or SDK users may need to act on:

- **Project-load semantics**: Hosts are now required to send the `instanceChanged` action with `kOfxPropChangeReason` = `kOfxChangePluginEdited` when a clip or parameter was changed while loading a project (issue #184).
- **Windows ARM64 plugin search**: An Arm64EC host should load plug-ins from the new `Win-arm64ec` folder. An x64 host should detect when it is running under Arm64 emulation and then also check `Win-arm64ec`, preferring a native Arm64EC plug-in there over the x64 plug-in in `Win64`. Plug-in installers should put Arm64EC (or Arm64X) binaries in `Win-arm64ec` and keep x64 binaries in `Win64` (issue #160).
- **HostSupport descriptor inheritance**: An effect instance now inherits `kOfxImageEffectPropSupportsTiles` and the GPU `*RenderSupported` properties from the plugin descriptor instead of overriding them with a hard default, so values set only in describe are honoured (issue #177). The header docs now state this inheritance rule for hosts.
- **HostSupport: resource-owning classes are non-copyable, and two constructors are `explicit`** (NatronGitHub/openfx#222): `OFX::Binary`, `Memory::Instance`, `PluginHandle`, `Host` and `Plugin` are non-copyable (a copy unloaded the library, freed the memory or released the binary twice, or handed out the original host's properties), and `Binary(const std::string&)` and `PluginDesc(OfxPlugin*)` are `explicit`. Hosts rebuild against HostSupport; only code that copied those classes or converted to them implicitly breaks (Natron does neither).
- **HostSupport: `Host::preferOverlayInteractV1()`**: a host that implements the DrawSuite (`supportsDrawSuite()`) and also draws overlays with OpenGL can return true, so that when a plug-in sets both `kOfxImageEffectPluginPropOverlayInteractV1` and `kOfxImageEffectPluginPropOverlayInteractV2`, its V1 (OpenGL) entry is used: OpenGL can draw more than the DrawSuite. Plug-ins that only set V2 still get V2. The default (false) keeps V2 when both are set. Natron, whose viewer draws with OpenGL, will return true.
- **HostSupport: `kOfxActionLoad` and `kOfxActionDescribe` once per load of the binary**: the plug-in scan (`PluginCache::loadFromPlugin()`) used to send Load, Describe and Unload, then `ImageEffectPlugin::getPluginHandle()` sent Load and Describe again on the same descriptor, although the binary stayed loaded for the whole session ("This action will not be called again while the binary containing the plug-in remains loaded"). The second Describe appended the supported contexts and pixel depths again. Now the scan sends Load, Describe and Unload to each plug-in of a binary, and then really unloads the binary (the reference that `PluginBinary::loadPluginInfo()` took is released): the first use of a plug-in (`getPluginHandle()`, from `createInstance()` or `getContext()`) loads the binary again, with its `OfxSetHost`, Load and Describe, as for a plug-in known from the plug-in cache, and Unload is sent when the plug-in cache is deleted (`PluginCache::clearPluginCache()`). A host can return true from the new `Host::keepPluginsLoadedAfterScan()` to keep the scanned plug-ins loaded instead: one Load and Describe, and Unload at `PluginCache::clearPluginCache()`. Statically linked plug-ins always stay loaded. Before Describe, the base descriptor is reset in place to its initial state, so a plug-in doesn't see the values read from the cache or described during a previous load. After OfxSetHost, Load or Describe failed (Load and Describe failures are logged), `getPluginHandle()` returns NULL while the binary stays loaded ("no further actions will be passed to the plug-in"), and tries again after the binary was unloaded (e.g. after `kOfxStatErrMemory`). `ImageEffectPlugin` sends Unload before deleting its descriptors; after an Unload, the pointer properties of its base descriptor (overlay interact entry points...) are reset to NULL and its overlay descriptor is described again at the next use, as for a plug-in known from the cache. `Host::loadingStatus()` documents that the scan's Load and Describe happen after its `loading=true` call. Natron (2.6) uses the keep mode: it overrides `keepPluginsLoadedAfterScan()` to return true. Scan runs (no cache, or a changed binary) of the default mode pay the static initialisation and the Load of each plug-in twice (e.g. the G'MIC standard library is parsed twice). Hosts must be rebuilt (the layout of `ImageEffectPlugin`, `PluginBinary` and the `Host` vtable changed); the plug-in cache file format is unchanged, so no cache invalidation is needed.
- **Plug-ins in HostSupport hosts (scan runs)**: by default, a HostSupport host now unloads (`dlclose`/`FreeLibrary`) a binary after the scan, and loads it again (`dlopen`) when a plug-in is first used: a plug-in gets Load, Describe and Unload, then Load and Describe again. Its global state must be re-initialised from Load to Unload, not by static initialisers alone, and its static destructors run at the unload (on macOS, a binary with thread-local variables stays mapped, and its statics survive). This was already allowed by the specification, and it is what hosts that unload their plug-ins do.
- **Support: the host description is reset at the last Unload**: `OFX::getImageEffectHostDescription()` returns NULL after the last `kOfxActionUnload` of the binary's plug-ins, until the next `kOfxActionLoad` fetches it again (it used to keep the previous host's description, and a second Load logged "Tried to create host description when we already have one"). The load count is also undone when a plug-in's `load()` throws, so the next Load fetches the suites again.
- **HostSupport plug-in scan: `@` entries and non-bundles are skipped**: as the packaging spec requires ("Any bundle or sub-directory name starting with the character '@' is to be ignored"), `PluginCache::scanDirectory()` now skips every entry whose name starts with `@`, including bundles such as `@X.ofx.bundle`, which used to be loaded. A directory is only a bundle if its name ends with `.ofx.bundle`: a directory such as `X.ofx.bundle.old` is no longer loaded (it was recorded as an invalid binary), and is scanned as a plain directory (NatronGitHub/openfx#184, NatronGitHub/Natron#1380).
- **HostSupport: the param, progress and timeline suites reject NULL or describe-time (descriptor) handles, and NULL names**: as `clipGetHandle()`, `imageMemoryAlloc()` (NatronGitHub/openfx#178) and `paramEditBegin()`/`paramEditEnd()` (NatronGitHub/openfx#180) already do, these functions now check what kind of object a handle is (with `dynamic_cast` from the base class whose address the handle is) instead of reinterpreting it. `Param::Base` and `ImageEffect::Base` have no magic number, so any other pointer is still undefined behaviour. `paramDefine()` returns `kOfxStatErrBadHandle` for an instance's param set, `kOfxStatErrUnknown` for a NULL type and `kOfxStatErrValue` for a NULL name, and sets `*propertySet` to NULL whenever it fails (except `kOfxStatErrExists`, which still hands back the existing param's). `paramGetHandle()` returns `kOfxStatErrUnknown` for a NULL name (it crashed), and sets `*param` and `*propertySet` to NULL whenever it fails; it keeps accepting a descriptor's param set at describe time, which the Support library's parametric params need. The value, key and copy functions (`paramGetValue*()`, `paramGetDerivative()`, `paramGetIntegral()`, `paramSetValue*()`, `paramGetNumKeys()`, `paramGetKeyTime()`, `paramGetKeyIndex()`, `paramDeleteKey()`, `paramDeleteAllKeys()`, `paramCopy()`) return `kOfxStatErrBadHandle` for a describe-time param descriptor handle, which they used to use as an instance, and `paramGetNumKeys()`, `paramGetKeyTime()` and `paramGetKeyIndex()` for a NULL return pointer; `paramGetPropertySet()` keeps accepting descriptors. Plug-ins that call these functions correctly see no change (NatronGitHub/openfx#187).
- **HostSupport: `paramDefine()` returns `kOfxStatErrUnknown` for an unknown param type**: "kOfxStatErrUnknown - if the type is unknown". A type that is none of the `kOfxParamType*` used to give `kOfxStatErrUnsupported`, after `SetDescriptor::paramDefine()` returned NULL, and crashed hosts whose `paramDefine()` override uses the descriptor that the base class returns (Natron). Host overrides of `SetDescriptor::paramDefine()` no longer get unknown types; a known type that the host can't instantiate (NULL from `paramDefine()`, e.g. a parametric param without `OFX_SUPPORTS_PARAMETRIC`) is still `kOfxStatErrUnsupported` (NatronGitHub/openfx#187).

They now return `kOfxStatErrBadHandle` for a NULL handle or for an interact descriptor's handle (the one passed to the interact's `kOfxActionDescribe`), which they used as an instance. `interactGetPropertySet()` keeps accepting descriptors, returns `kOfxStatErrBadHandle` for a NULL handle or a NULL `property`, and sets `*property` to NULL whenever it fails. The DrawSuite functions return `kOfxStatFailed` ("failure, e.g. if function is called outside kOfxInteractActionDraw"; `ofxDrawSuite.h` has no bad-handle status) for a NULL context, a context that is not an interact instance, or an instance outside its draw action. The handle is checked with `dynamic_cast` from `Interact::Base`, the class whose address the handle is. `Interact::Base` has no magic number, so any other pointer is still undefined behaviour. `kOfxInteractPropDrawContext` is now set to `Interact::Base::getHandle()`, which is the same address as before. `suiteHandleChecks` checks these statuses, and the progress and timeline functions on a real effect instance (the Invert plug-in, found through `OFX_PLUGIN_PATH`, which `hostdemo-checks.sh` now passes): a NULL progress label or message id, `gotoTime(NaN)`, and NULL `time`, `firstTime` or `lastTime` pointers on a valid handle.

It is still `noexcept(false)` under C++11 and later, and still empty on Windows. Overrides that use the macro need no change.

The destructor still sends the action if it was not sent, but only as a safety net: by then the overridden virtuals are gone. `Interact::Instance` has no `destroyInstanceAction()`; its destructor sends the action, and its documentation now states that limit.

Plug-ins only need a clean rebuild; repositories that list the Support sources need no change (the font header moved to `include/`, which is on every include path).
- **DrawSuite ellipses**: the ellipse tessellation is now `OFX::DrawSuiteOpenGL::ellipseSegmentCount()`, shared by Support and the hosts that use the core: the largest radius r in screen pixels (canonical radius / pixel scale), 8 vertices if r <= 1/4 or r is not finite, else ceil(2 pi / (2 acos(1 - 0.25 / r))) clamped to [8, 4096], so that the segments are within 1/4 screen pixel of the ellipse (e.g. 15 vertices for r = 10, 45 for 100, 141 for 1000, 1405 for 1e5). This is what Support's OpenGL backend already did; hosts (Natron used about one segment per 2 pixels of perimeter, 16 to 1024) get the same tessellation as Support.
- **CMake 3.21 or newer**: the CMake build, `cmake/OpenFX.cmake` and `cmake/OpenFXExpat.cmake` need CMake 3.21 (they needed 3.16). Every target platform ships it: Rocky Linux 8.8+ and 9 (3.26), Ubuntu 22.04 (3.22) and 24.04 (3.28), MacPorts, MSYS2 and the GitHub runners; only Ubuntu 20.04 (3.16) drops out. The modules stop with an error under an older CMake (also when they come from `find_package(openfx)`), and run their code and functions with the policies of CMake 3.21...3.31 (e.g. CMP0126 and CMP0177), whatever the project's minimum. Plug-in and host projects should raise their `cmake_minimum_required` to `3.21...3.31`, so that their own code gets the same policies. The compatibility code for older CMake versions is removed. Policies newer than 3.31 keep their old behaviour until the upper bound is raised after testing a newer CMake. With CMP0126, a normal variable that a `find_package(openfx)` consumer sets before (e.g. `OFX_CXX_STANDARD`) now wins over the module's cache default. openfx-arena's `cmake_minimum_required(VERSION 3.1)` already fails under CMake 4, so moving to 3.21 also fixes that.

Hosts rebuild against HostSupport; subclasses of `Property` or of `PropertyTemplate` (`Property::Int`, `Double`, `String`, `Pointer`) that override `deepCopy()` or `getStringValue()` must add `const` (Natron has none).
- **Conan package layout**: Restructured the recipe to the standard Conan Center Index layout (headers under `include/`, libs and CMake module under `lib/`, licenses under `licenses/`) (issues #238, #246), and example-only dependencies (OpenGL, CImg, spdlog, OpenCL) are no longer imposed on consumers — they're gated behind a new `build_examples` option (#253).
- **HostSupport: `gotoTime()` rejects infinite times; the progress and timeline suites pass some host statuses through**: `gotoTime()` returns `kOfxStatErrValue` ("the time was an illegal value") for ±infinity, as for NaN, and when the host's `timeLineGotoTime()` throws an `OFX::Host::Property::Exception` with `kOfxStatErrValue`. `progressUpdate()` and `progressEnd()` return `kOfxStatErrBadHandle` ("the progress handle was invalid") when the host's `progressUpdate()`/`progressEnd()` throws a `Property::Exception` with that status, e.g. without an ongoing progress. Any other exception still gives `kOfxStatFailed`. A host that throws these statuses now has the plug-in see them instead of `kOfxStatFailed` (NatronGitHub/Natron#1385, NatronGitHub/Natron#1483).
- **HostSupport: "instance (read only)" parameter properties are plug-in read-only on instances**: a parameter instance copies the descriptor's properties, where the plug-in may write them, so the properties that OFX 1.5.1 `ofxParam.h` and `ofxParametricParam.h` document as "plugin parameter descriptor (read/write) and instance (read only)" (or "instance (read only)") were writable on instances, with no effect. Under the default `ePluginReadOnlyEnforce` policy a plug-in write returns `kOfxStatErrValue` (the Support library then throws `OFX::Exception::PropertyValueIllegalToHost`, or logs if `throwOnFailure` is false); under `ePluginReadOnlyWarn` it is accepted with a warning. The host's C++ setters are not restricted. `kOfxParamPropGroupOpen` stays writable on instances, for the Natron toolbar and dialog extensions, which `ofxNatron.h` now documents. The read-only warning is now thread-safe (C++11 builds) (NatronGitHub/Natron#1385).
- **HostSupport: `std::bad_alloc` gives `kOfxStatErrMemory` in the image, RoD and texture functions**: `clipGetImage()`, `clipGetRegionOfDefinition()`, `imageMemoryLock()`, `clipLoadTexture()` (OpenGL render suite), `clipGetImagePlane()` and the view `clipGetRegionOfDefinition()` (Nuke image plane suite) and `clipGetStereoscopicImage()` (Vegas) used to return `kOfxStatErrBadHandle` for every exception the host threw, `std::bad_alloc` included. They now return `kOfxStatErrMemory` ("the host had not enough memory to complete the operation, plugin should abort whatever it was doing") for `std::bad_alloc`, with the returned image, texture or pointer set to NULL; `clipLoadTexture()` also sets it to NULL for an invalid clip. Plug-ins still abort the render, now with the out-of-memory status (NatronGitHub/Natron#1385).
- **HostSupport: `kOfxImageEffectPropThumbnailRender` in the `kOfxImageEffectActionEndSequenceRender` inArgs**: OFX 1.5.1 lists it ("(optional) if the host considers this render a "thumbnail"") in the inArgs of EndSequenceRender, and `Instance::endRenderAction()` didn't set it. It is now set like in BeginSequenceRender, from `Instance::isThumbnailRender()` when End is called: a host that keeps its `ThumbnailRenderScope` from `beginRenderAction()` to `endRenderAction()` gets the same value in both. Plug-ins see one more optional property in that action (NatronGitHub/Natron#1385).
- **HostSupport: `memoryFree()` returns `kOfxStatErrBadHandle` for pointers that `memoryAlloc()` didn't return**: the memory suite was `malloc()`/`free()`. Each block now starts with a header holding a magic number, and the pointer handed out is `malloc()` + 64 (or + `alignof(std::max_align_t)` if larger): it keeps any alignment of `malloc()`'s result up to 64 bytes, so large blocks that `malloc()` aligns to a page stay cache-line and AVX-512 aligned, and small blocks stay "aligned for any use"; the cost is 64 bytes per block. `memoryFree()` returns `kOfxStatErrBadHandle` ("allocatedData was not a valid pointer returned by OfxMemorySuiteV1::memoryAlloc") for NULL and for a pointer without the header, instead of passing it to `free()`. A plug-in that mixes allocators, which the spec already forbade but which used to work, now breaks: freeing a `memoryAlloc()` block with `free()` (e.g. from static destructors after the Support library has reset its memory suite pointer at unload) aborts or corrupts the heap, and passing a `malloc()`ed pointer to `memoryFree()` gets `kOfxStatErrBadHandle` and leaks. `memoryAlloc()` with a NULL `allocatedData` returns `kOfxStatErrBadHandle` (a programmer error; not among its documented returns), and `kOfxStatErrMemory` if the size overflows (NatronGitHub/Natron#1385).
- **HostSupport: `OfxImageEffectSuiteV1::abort()` returns 0 or 1; exception safety of the property set copy and of the plug-in scan** (NatronGitHub/openfx#232): `abort()` follows the spec ("0 if the effect should continue whatever processing it is doing, 1 if the effect should abort", `ofxImageEffect.h`): a handle that is not an effect instance (NULL, a descriptor), or an exception from the host's `Instance::abort()`, gives 1 (it was `kOfxStatErrBadHandle`, 9), and a non-zero `Instance::abort()` gives 1; plug-ins that test `!= 0` see no change. The copy of a property set (`Set(const Set&)`) deletes the properties it copied and rethrows if a copy throws, and throws `std::bad_alloc` if a `deepCopy()` returns NULL (it gave an empty set). The plug-in scan closes its directories and releases the binary it was loading if it throws (also for a changed cached binary and for the statically linked plug-ins), and the cleanup of a `PluginBinary` never throws. The "failing in" `printf`s of `ImageEffect::Instance` are only printed with `OFX_DEBUG_PROPERTIES`.
- **Natron `kNatronOfxImageEffectPropDeprecated` removed; use the standard `kOfxImageEffectPluginPropObsolete`**: the two had the same meaning (the host hides the plug-in from new use, and still loads it in existing projects). `include/ofxNatron.h` no longer defines `kNatronOfxImageEffectPropDeprecated` (there is no alias, and it is not in `ofxOld.h`), Support no longer has `ImageEffectDescriptor::setIsDeprecated()` (call `setIsObsolete()`), and HostSupport no longer declares the descriptor property nor has `ImageEffect::Base::isDeprecated()` (call `isObsolete()`). A plug-in that still sets the old property gets `kOfxStatErrUnknown` from a HostSupport host: Support doesn't throw and current Support logs nothing; debug builds of Support older than e979dca3 log one ERROR line. Removing `Base::isDeprecated()` is a source break for hosts, not an ABI break (a non-virtual function of a static library). Natron 2.5 does not run the Natron 2.6 plug-ins, so no backward compatibility is kept. The `kOfxImageEffectPluginPropObsolete` doc (header, Support and HostSupport) says that this fork relaxes upstream's rule that one version in the bundle must not be obsolete: a plug-in superseded by another plug-in or by a host-internal node may set it too, even as its only version, e.g. openfx-io's ReadEXR, superseded by ReadOIIO (upstream openfx#221) (NatronGitHub/openfx#198).
- **HostSupport: `kOfxImageEffectPropBehaviourWhenUnlicensed` in the BeginSequenceRender and Render inArgs**: the new virtual `ImageEffect::Instance::getBehaviourWhenUnlicensed()` returns the host's behaviour, `kOfxUnlicensedContinue` or `kOfxUnlicensedFail`, and `beginRenderAction()` and `renderAction()` put it in their inArgs (`setBehaviourWhenUnlicensedArg()`). The default returns "", and the property is then not in the inArgs, which the spec allows: "If kOfxImageEffectPropBehaviourWhenUnlicensed is not set (indicating the host has not implemented this functionality): plug-in should render an image (typically watermarked or a placeholder) and return kOfxStatOK". Any other value is not sent either. It may be called from render threads, so it must be thread-safe, and a host that returns Continue or Fail must handle `kOfxStatUnlicensed` from the render actions. Hosts must be rebuilt (the `Instance` vtable changed) (NatronGitHub/openfx#198).
- **HostSupport: `kOfxParamPropColourManagement` on RGB and RGBA params, opt-in per host**: the new virtual `ImageEffect::Host::supportsParamColourManagement()` (default false) says whether the host implements it. A host opts in only if it converts `kOfxParamColourManagementManaged` (ACES2065-1) and `kOfxParamColourManagementSRGB` values for its swatches and colour pickers, stores them as such, and converts the values of legacy projects. Then RGB and RGBA descriptors declare the property with the default `kOfxParamColourManagementNone` ("It defaults to ::kOfxParamColourManagementNone, so existing plug-ins are unaffected"), a plug-in can set it to any of the three values ("A host that supports this property MUST accept all three values"), and it is read-only for the plug-in on instances ("A plug-in MUST NOT change it on a parameter instance"). Otherwise the property is absent, and a plug-in's set fails (`kOfxStatErrUnknown`), as before: "A host that does not implement it will fail the set; in that case the plug-in MUST fall back to ::kOfxParamColourManagementNone behaviour". hostDemo and the ofxh Python bindings' host opt in (not with the OFX 1.4 profile); Natron will opt in with NatronGitHub/Natron#1141. Hosts must be rebuilt (the `ImageEffect::Host` vtable changed) (NatronGitHub/openfx#198).
- **Support: property validation knows the next-release properties**: `ofxsPropertyValidation.cpp` (debug builds) checks `kOfxImageEffectPluginPropObsolete` and `kOfxImageEffectPropMetalTextureSupported` on the plug-in descriptor (defaults 0 and "false"), `kOfxImageEffectPropMetalTextureSupported` on the host, `kOfxParamInterpType` on 1D integer and double params (default `kOfxParamInterpTypeLinear`), `kOfxParamPropColourManagement` on RGB and RGBA params (default `kOfxParamColourManagementNone`), `kOfxImageClipPropDisplayTimeOffset` on clip instances, `kOfxImageEffectPropMetalTextureEnabled` in the Render, BeginSequenceRender and EndSequenceRender inArgs, and `kOfxImageEffectPropBehaviourWhenUnlicensed` in the Render and BeginSequenceRender inArgs. They have no OFX version number yet, so a host may lack them: they are only validated if the host has them (NatronGitHub/openfx#198).
- **`linuxCheckBundle.sh`: the OpenCL ICD loader is no longer a system library**: `libOpenCL.so.1` is the vendor-neutral OpenCL ICD loader (ocl-icd, or the Khronos OpenCL-ICD-Loader), not a driver library: no default EL9 or Ubuntu install has it, and it loads the vendor drivers itself through `/etc/OpenCL/vendors/*.icd`. The checker now asks for it to be bundled, like any other library (or listed in `OFX_ABI_OPTIONAL_LIBS`): its "never bundle" rule had installers skip it, and openfx-io's IO.ofx, whose FFmpeg's libavutil needs it on Ubuntu, failed to load where it wasn't installed (NatronGitHub/openfx-io#270). New system libraries, which must never be bundled: the OpenCL vendor ICDs (`libnvidia-opencl`, `libamdocl*`, `libigdrcl`, `libintelocl`, `libMesaOpenCL`, `libRusticlOpenCL`, `libpocl`), NVIDIA's other driver libraries (`libnvidia-*`, `libnvcuvid`; `libcuda` already was), `libdrm`, `libdrm_*`, and Mesa's `libgbm` and `libglapi` (the system Mesa drivers need the system's copies; EL9's minimal install doesn't have them, as it doesn't have libGL), systemd's `libudev` (it reads the running udev's private database) and `libselinux` (in every EL9 and Ubuntu install). An installer that bundled one of them must stop bundling it. To bundle the loader, copy `libOpenCL.so.1` (EL9 package `ocl-icd`, BSD-2-Clause: ship its licence) to `<bundle>/Libraries`; to accept it from the system instead, set `OFX_ABI_OPTIONAL_LIBS`, which replaces the default list, e.g. `OFX_ABI_OPTIONAL_LIBS="libz.so.1 libOpenCL.so.1"`. A `--no-needed` run doesn't detect an unbundled `libOpenCL.so.1`.
- **CMake, Linux and FreeBSD: build-tree plug-ins get their install rpath (`OFX_PLUGIN_BUILD_WITH_INSTALL_RPATH`, default ON)**: `add_ofx_plugin` sets `BUILD_WITH_INSTALL_RPATH`, so a build-tree plug-in has the same RUNPATH as the installed one (e.g. `$ORIGIN/../../Libraries`, plus the directories of linked libraries outside the project) instead of CMake's build rpath padded with `:` for the install-time rewrite: an empty RUNPATH entry means the current directory to the loader. While it is ON, `BUILD_RPATH`, `CMAKE_BUILD_RPATH` and `CMAKE_SKIP_BUILD_RPATH` don't affect the plug-ins. `INSTALL_RPATH_USE_LINK_PATH` skips the link directories inside the source and binary trees, so a plug-in that, run from the build tree, needs a library from an in-tree prefix (e.g. a dependency built in the checkout) must get that directory with `add_ofx_plugin(RPATH)` or `OFX_PLUGIN_RPATH`, and one that needs a shared library built by the project needs `-DOFX_PLUGIN_BUILD_WITH_INSTALL_RPATH=OFF`. None of openfx-misc, openfx-io, openfx-arena, openfx-gmic or openfx-supportext builds a shared library for its plug-ins; openfx-io's CI passes its in-tree `SeExprBuild` prefix with `RPATH`, so it is unaffected, and a local in-tree run of a configuration that links an in-tree FFmpeg prefix (e.g. `FFmpegBuild`) needs it in `OFX_PLUGIN_RPATH`. Still, ship, upload and check (`linuxCheckBundle.sh`) only the installed tree (`cmake --install` output or the archive), never the build tree (openfx-gmic#119: its build-tree Linux artifact had padded RUNPATHs and no Info.plist). macOS and Windows are unchanged.

## Documentation Improvements

- **Support and HostSupport configuration macros**: the README now states that the `OFX_EXTENSIONS_*`/`OFX_SUPPORTS_*` definitions change class layouts, so every source of a binary, Support and HostSupport included, must be compiled with the same set. A host (HostSupport) and its plug-ins (Support) are separate binaries and may use different sets. With CMake, choose them only through openfx's options (`openfx::Api`, `openfx::Support` and `openfx::HostSupport` pass them on), never on a target that links those libraries or on a single file; a build that compiles the Support or HostSupport sources itself (Makefile, qmake, a CMake target that lists them) uses one set for all the sources of each binary. The Makefiles define none by default (`CXXFLAGS_EXTRA`, `OPTIMISE`). A mismatch is not detected at build time (NatronGitHub/openfx#226).
