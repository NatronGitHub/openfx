# openfx-cpp in the NatronGitHub fork

`openfx-cpp/` is upstream's header-only C++17 layer for type-safe access to properties, property sets and suites (AcademySoftwareFoundation/openfx). It is purely additive: `Support/` and `HostSupport/` are unchanged, and consumers that use them are not affected.

## Where it comes from
- `include/openfx/ofxPropsMetadata.h`, `ofxPropsBySet.h`, `ofxPropSetAccessors.h` and `ofxPropSetAccessorsHost.h` are generated by `scripts/gen-props.py` from the `@propdef` and `@propset` metadata of the fork's `include/ofx*.h`. CI checks that they are up to date, and that they compile with none of the macros below, with each one alone and with all of them (build.yml).
- The runtime headers come from upstream's `props-metadata` branch (473aa340), because upstream `main` contains the generated headers but not the headers they include: `ofxPropsAccess.h`, `ofxSpan.h`, `ofxLog.h`, `ofxSuites.h`, `ofxClip.h`, `ofxImage.h`, `ofxExceptions.h`, `ofxMisc.h`, `ofxStatusStrings.h`, and the READMEs.
- `examples/host-specific-props/` comes from upstream `main`. `examples/test-props/` is upstream's TestProps plug-in (`props-metadata:Examples/TestProps`), a property compliance tester built on this layer.
- `third_party/tcb/span.hpp` is tcbrindle/span 836dc6a0 (Boost Software License 1.0, see `third_party/tcb/LICENSE_1_0.txt`). It is the version upstream gets from conan as `tcb-span/cci.20220616`, and provides `openfx::span` before C++20.

## Fork adaptations
- `ofxPropsAccess.h`: `propGetString` takes `const char **` in the fork's `ofxProperty.h` and `char **` upstream. The `detail::StringOut` adapter converts to either.
- `ofxSuites.h` includes `ofxImageEffect.h` before `ofxDialog.h`, because the fork's `OfxDialogSuiteV2` uses `OfxImageEffectHandle`.
- `ofxSuites.h` includes `<stdexcept>` (for `std::out_of_range`) and `ofxPropsAccess.h` includes `<cstring>` (for `std::strcmp`). Upstream's copies (`props-metadata` 473aa340) rely on libc++ including them transitively, and `ofxSuites.h` doesn't compile with libstdc++ (g++).
- `include/ofxImageEffect.h` defines `kOfxImageEffectPropNoSpatialAwareness` in every build, not only under `OFX_EXTENSIONS_RESOLVE`, because it has been standard since OFX 1.5.1.
- `scripts/gen-props.py` never names a generated getter after a C++ keyword. Upstream generates `T default(...)` for `kOfxParamPropDefault` in `ofxPropSetAccessorsHost.h`, which doesn't compile; here it's `defaultValue()`. Setters are unchanged (`setDefault`).
- The generated headers honour these macros (`GUARD_MACROS` in `scripts/ofx_fork_props.py`, which defines the mapping in one place, with a comment for each):
  - the fork's extensions, `EXTENSION_MACROS`: `OFX_EXTENSIONS_NATRON`, `_NUKE`, `_RESOLVE`, `_TUTTLE`, `_VEGAS`, and `OFX_SUPPORTS_PARAMETRIC_V2`, chosen by the `extension:` key of the property's `@propdef`. `gen-props.py` reads these properties from `include/ofx*.h`, `include/nuke/` and `include/tuttle/`, and includes each extension's own headers (`ofxNatron.h`, `ofxSonyVegas.h`, `nuke/*.h`, `tuttle/ofxReadWrite.h`) under its macro;
  - the optional features, `FEATURE_MACROS`, which guard only the properties that matter only when the feature is used: the in-render properties, the plug-in's OpenGL bit depths and the parametric parameters' own properties:
    - `OFX_SUPPORTS_OPENGLRENDER`: `OpenGLEnabled`, `OpenGLTextureIndex`, `OpenGLTextureTarget` and `OfxOpenGLPropPixelDepth`;
    - `OFX_SUPPORTS_OPENCLRENDER`: `OpenCLEnabled`, `OpenCLCommandQueue` and `OpenCLImage`;
    - `OFX_SUPPORTS_CUDARENDER`: `CudaEnabled` and `CudaStream`;
    - `OFX_SUPPORTS_PARAMETRIC`: the parametric parameters' own properties of `ofxParametricParam.h` (dimension, interact background, range, UI colour).

    `include/` defines these properties unconditionally; only the openfx-cpp headers guard them. This is deliberate, even though HostSupport sets the OpenCL and CUDA in-render properties unguarded: HostSupport doesn't use openfx-cpp, and a plug-in built without the feature can't name them.
  - The capability flags are never guarded, because every host has them and their "false" (or 0) means the feature is absent (`ofxGPURender.h`: '"false" - in which case the host or plug-in does not support OpenGL accelerated rendering'). They are `OpenGLRenderSupported`, `OpenCLRenderSupported`, `OpenCLSupported`, `CudaRenderSupported`, `CudaStreamSupported`, the Metal flags, `CPURenderSupported` and `OfxParamHostPropSupportsParametricAnimation`. The Metal properties have no `OFX_SUPPORTS_` macro and are not guarded.
  - `UNGUARDED_FEATURE_PROPERTIES` lists them, and `gen-props.py` stops on a property of `ofxGPURender.h` or `ofxParametricParam.h` that neither list classifies.
  - `OFX_SUPPORTS_DIALOG`, `OFX_SUPPORTS_DIALOG_V1` and `OFX_SUPPORTS_MULTITHREAD` guard no property (their headers define none).

  Every table that names a guarded property's `PropId` has its entry under the macro: in `ofxPropsMetadata.h` (enum, enum values, types, `prop_defs`, traits, `static_assert`s), and in `ofxPropsBySet.h` and the two accessor headers (set entries, accessor methods). Any subset of the macros compiles. The unguarded properties come first, so their `PropId`s don't depend on the macros. Then come each macro's, in the macros' alphabetical order, so a guarded property's `PropId` depends on which macros before it are set. Build every translation unit of a binary that includes these headers with the same macros (as for the rest of the fork's extension and feature code): with different ones, `PropId` and `prop_defs` have different definitions, an ODR violation even if no `PropId` is passed between them. It fails silently: two translation units built with different macro sets can give the same `PropId` to different properties (for example `NatronOfxBooleanParamPropIsToggableButton` with `OFX_EXTENSIONS_NATRON`, and `OfxImageEffectPropOpenGLEnabled` with `OFX_SUPPORTS_OPENGLRENDER`). A template keyed on `PropId` then silently uses one translation unit's property in the other, and the linker doesn't detect it. The same macro set in every translation unit of a binary is a hard requirement. `PropId`s never leave a binary: the host is accessed by property name. No `@propset` lists an extension property; `gen-props.py` stops if one does. Properties whose string isn't a C++ name (the Nuke extension's `uk.co.thefoundry....`) are named after their macro, without the `k`.
- The fork's `@propset ImageEffectHost` lists `OfxImageEffectPropSupportedPixelDepths`, which upstream's omits although the property is supported "by a plug-in or host" (upstream's doc; the fork's 1.4-era header says "host descriptor (read only)"), so the generated headers list it in the `ImageEffectHost` property set.
- `examples/host-specific-props/example-usage.cpp`: fixed an ambiguous `PropId` (both `openfx` and `myhost` in scope). `examples/test-props`: updated for upstream's rename of `ParamDouble1D` to `ParamsDouble1D`.

## Regenerating
`gen-props.py` reads the `@propdef` and `@propset` metadata in `include/ofx*.h`. Run `make regen` (or `python scripts/gen-props.py`) after changing it, and commit the generated headers with the change, as upstream does; CI fails if they are out of date. `gen-props.py`'s own checks follow upstream's rules and report the fork's names that aren't properties and the extension properties that no property set lists: `scripts/check-props.py` is the fork's check.

## Building and testing (no CMake needed)
```sh
port_switch; make -C openfx-cpp check CXX=clang++-mp-22                      # every header on its own, plus the examples
port_switch; make -C openfx-cpp check CXX=clang++-mp-22 CXXSTD=c++20
port_switch; make -C openfx-cpp check CXX=clang++-mp-22 EXTRA_CXXFLAGS="-DOFX_EXTENSIONS_NATRON -DOFX_EXTENSIONS_NUKE -DOFX_EXTENSIONS_RESOLVE"
port_switch; make -C openfx-cpp testprops CXX=clang++-mp-22                  # build/TestProps.ofx.bundle
port_switch; make -C openfx-cpp regen PYTHON=/path/to/python-with-pyyaml
```
To run TestProps, point a host at `openfx-cpp/build` (`OFX_PLUGIN_PATH`). The plug-in id is `net.sf.openfx:PropertyTestPlugin`. It logs a compliance report for each property set it sees.
